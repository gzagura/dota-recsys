# Dota 2 Draft Recommender

Контекстно-зависимая рекомендательная система выбора героя в Dota 2
на основе анализа текущего драфта, синергий/контрпиков и истории игрока.
Инференс — через веб-интерфейс: сетка портретов, как на экране пика,
драфт вводится вручную в реальном времени.

## Гипотеза

Рекомендация, учитывающая контекст текущего драфта (кто уже выбран
союзниками/врагами) и профиль конкретного игрока, даёт более
релевантные предложения героя, чем baseline на основе общего
winrate героя без контекста.

## Уровни модели (сравниваются между собой в работе)

| Уровень | Что учитывает | Метод | Статус |
|---|---|---|---|
| L0 (baseline) | Только общий winrate героя | Сортировка по статистике | реализован |
| L1 | Синергия союзников + контрпики врагов | Попарные winrate-дельты | реализован |
| L2 | L1 + профиль игрока (его winrate/роль/опыт по героям) | Взвешенная комбинация фич | реализован |
| L3 | Полный контекст драфта: синергия + контрпики + стадия драфта + ролевой состав | LightGBM | реализован |

Уровень, который поднимает сайт, задаётся в `configs/config.yaml` →
`model.level` (`L0` / `L1` / `L2` / `L3`). Интерфейс `recommend()` у всех
уровней одинаковый, поэтому переключение не требует правок в коде сайта.

## L3: LightGBM на агрегированных фичах драфта

### Постановка задачи

L3 решает задачу бинарной классификации: по кандидату и контексту драфта
предсказать вероятность победы его команды. Рекомендация получается
ранжированием — все свободные герои прогоняются через модель в текущем
контексте, наверх идут те, у кого выше `P(win)`.

Метка берётся из данных как есть (победа/поражение), экспертная разметка
«хороший/плохой пик» не требуется.

### Чем L3 отличается от L1/L2

L1/L2 складывают синергию и контрпик с **фиксированными** весами
(`w_synergy`, `w_counter`), заданными в конфиге. L3 обучает нелинейную
функцию от тех же величин плюс стадия драфта, ролевой состав команды,
сторона и атрибут героя — то есть сам выясняет, когда синергия важнее
контрпика и как это зависит от момента драфта.

### Почему агрегаты, а не one-hot драфта

Прямое кодирование драфта — это 2 × 124 бинарных признака на пример.
На объёмах, доступных через бесплатный OpenDota (десятки тысяч матчей),
такая размерность переобучается. Вместо этого контекст сворачивается в
~40 плотных агрегатов (`src/features/draft_features.py`):

| Группа | Признаки |
|---|---|
| Кандидат | `hero_id` (категориальный), `base_wr`, `pick_rate`, `primary_attr_code`, 9 флагов ролей |
| Синергия с союзниками | `syn_sum`, `syn_mean`, `syn_max`, `syn_min` |
| Контрпик против врагов | `ctr_sum`, `ctr_mean`, `ctr_max`, `ctr_min` |
| Стадия драфта | `n_allies`, `n_enemies`, `is_radiant` |
| Состав своей команды | `ally_base_wr_mean`, `enemy_base_wr_mean`, 9 счётчиков ролей союзников |

Один и тот же класс `DraftFeatureBuilder` считает фичи и при обучении, и
при инференсе — это исключает train/serve skew (расхождение формул между
обучением и боевым режимом).

### Как из матча получается обучающий пример

Один матч (10 героев + исход) даёт 10 примеров: каждый герой по очереди
считается «кандидатом», остальные четверо его команды — союзниками,
пятёрка соперника — врагами, метка = победила ли его команда. Выборка
получается сбалансированной по построению (5 победивших + 5 проигравших).

В бою сайт работает с **неполным** драфтом, поэтому для каждого примера
случайно «отматывается» стадия драфта: из союзников и врагов берётся
случайное подмножество, а его размеры подаются в модель признаками
`n_allies` / `n_enemies`. Число врагов сэмплируется рядом с числом
союзников (±1) — так имитируются поочерёдные пики команд.

### Защита от утечки данных

1. **Временной сплит.** Матчи сортируются по `match_id` (возрастает со
   временем), последние `val_fraction` идут в валидацию. Случайный сплит
   здесь дал бы завышенные метрики: мета Dota меняется от патча к патчу.
2. **Матрицы считаются только по train-части.** Иначе синергия, попавшая
   в фичи примера, уже содержала бы исход этого самого матча.
   Артефакты train-части сохраняются отдельно (`train_*.parquet`) — на них
   же считается ablation, чтобы L0/L1 и L3 сравнивались в равных условиях.

### Сглаживание попарной статистики

Winrate пары оценивается не как `wins / games`, а со сжатием к базовому
winrate героя с весом `prior_weight` (эмпирический байес):

```
synergy[i][j] = (wins_ij + prior * base_wr_i) / (games_ij + prior) - base_wr_i
```

Пара, сыгранная 3 раза, не получает дельту +50%, но и не выбрасывается
жёстким порогом — её вклад просто затухает до нуля.

### Персонализация в L3

`/publicMatches` не содержит `account_id`, поэтому профиль игрока по этим
данным обучить нельзя. Персонализация навешивается поверх предсказания
как аддитивная поправка со сглаживанием по числу игр:

```
score = P(win) + w_player * (сглаженный winrate игрока по герою - 0.5)
```

При `w_player = 0` получается чистый L3.

## Метрики оценки

- **AUC / logloss / accuracy** предсказания исхода матча на отложенных по
  времени матчах. Точка отсчёта печатается рядом (`val_auc_base_wr_only`):
  AUC того же предсказания по одному лишь базовому winrate кандидата.
  Если L3 её не бьёт — контекст драфта моделью не выучен.
- **Hit Rate@K / MRR** — попадание реального пика победившей команды в
  топ-K рекомендаций (`src/models/evaluate_ablation.py`). В отчёт
  добавляется строка `random` — уровень случайного угадывания.
- **Ablation**: L0 vs L1 vs L3 на одних и тех же ситуациях драфта и на
  одной и той же train-статистике.
- Эмпирика: N реальных игр самого автора с зафиксированными
  результатами (лог в `data/manual_eval_log.csv`).

Метрика Hit Rate измеряет совпадение с реальным пиком, а реальный пик —
не эталон оптимальности, а лишь пик, приведший к победе. Поэтому метрика
частично вознаграждает популярность героя; интерпретировать её нужно
вместе с AUC.

## Известные ограничения (см. раздел "Выводы" в работе)

- Нет открытого live-API для драфт-фазы → ввод драфта на сайте ручной.
- GSI (Game State Integration) покрывает in-game события, но не
  pick/ban стадию надёжно — вынесено как направление развития.
- Данные OpenDota смещены в сторону конкретных MMR-бракетов —
  бракет выборки задаётся в `opendota.public_matches.min_rank_tier` и
  должен быть указан в разделе методологии.
- `/publicMatches` не отдаёт **порядок** пиков, поэтому стадия драфта при
  обучении моделируется случайным подмножеством, а не реальной
  последовательностью выбора. Настоящий порядок доступен только в
  распарсенных про-матчах — направление развития.
- Бан-фаза не моделируется вообще: в данных публичных матчей её нет.
- L2 не участвует в ablation: для чужих публичных матчей профиля игрока
  не существует, персонализацию корректно мерить только на истории автора.

## Структура репозитория

```
data/                    # сырые и обработанные данные (в .gitignore)
src/data_pipeline/        # сбор и очистка данных из OpenDota API
  fetch_heroes.py           # справочник героев
  fetch_matches.py          # matchups + история игрока (L1/L2)
  fetch_public_matches.py   # публичные матчи с полными драфтами (L1/L3)
src/features/             # построение фич
  build_synergy_matrix.py   # матрицы синергии/контрпиков + hero_stats
  player_profile.py         # профиль игрока (L2)
  draft_features.py         # агрегированные фичи драфта (L3), train + serve
  build_training_dataset.py # обучающая выборка L3, временной сплит
src/models/               # модели и оценка
  baseline.py               # L0
  synergy_model.py          # L1 / L2
  l3_lgbm.py                # L3: обучение + инференс
  evaluate_ablation.py      # сравнение уровней по Hit Rate@K / MRR
src/service.py            # общий слой инференса: артефакты + ранжирование
src/profiles.py           # профили игроков по steam-id: OpenDota, кеш, фолбэк
src/hero_aliases.py       # русские имена и сленг («кристалка», «сф»)
src/web/                  # сайт
  app.py                    # FastAPI: /api/heroes, /api/profile, /api/recommend
  auth.py                   # логины друзей, scrypt-хеши, рейт-лимит
  static/index.html         # интерфейс драфта целиком, без сборки
notebooks/                # EDA, эксперименты, отчёты для курсовой
tests/                    # unit-тесты пайплайна, моделей, профилей и калитки
configs/                  # конфиги (config.yaml, users.json — оба вне git)
```

## Запуск

```bash
pip install -r requirements.txt
cp configs/config.example.yaml configs/config.yaml

# Шаг 1: справочники героев
python -m src.data_pipeline.fetch_heroes

# Шаг 2: данные.
#   matchups + история игрока (для L1 без синергии и для L2)
python -m src.data_pipeline.fetch_matches
#   публичные матчи с полными драфтами (нужны для синергии и для L3).
#   Долго: ~1 запрос/сек, 100 матчей за запрос. Докачка безопасна —
#   уже скачанные match_id пропускаются.
python -m src.data_pipeline.fetch_public_matches

# Шаг 3: матрицы синергии/контрпиков + базовая статистика героев
python -m src.features.build_synergy_matrix
python -m src.features.player_profile        # опционально, для L2

# Шаг 4: обучение L3
python -m src.features.build_training_dataset   # выборка + временной сплит
python -m src.models.l3_lgbm                    # обучение, метрики, важности

# Шаг 5: сравнение уровней (таблица для раздела с результатами)
python -m src.models.evaluate_ablation

# Шаг 6: учётки для тех, кому открываем доступ
python -m src.web.auth init я друг1 друг2

# Шаг 7: запуск сайта (уровень берётся из model.level в config.yaml)
python -m src.web.app        # http://127.0.0.1:8000
```

Для локальной возни калитку можно снять — тогда файл пользователей не нужен:

```bash
DRAFT_NO_AUTH=1 python -m src.web.app
```

Тесты:

```bash
python -m pytest tests/ -q
```

## Персонализация

Пользователь вводит свой Steam ID в шапке сайта (понимаются оба формата:
steam32 `118356858` и steam64 `76561198078622586`). Сервер один раз тянет
историю матчей из OpenDota, складывает профиль в `data/profiles/` и дальше
берёт его оттуда — сутки. Поправка к оценке кандидата:

```
score = P(win) + w_player * (сглаженный winrate игрока по герою - 0.5)
```

Сглаживание — приором в `player_prior_games` игр по 50%. Смысл: пока по
герою сыграно мало, личная статистика почти не двигает выдачу. Без приора
случайные 7 побед из 8 выкидывали бы героя на первое место вперёд
объективно более сильных.

Персонализация выключается сама, без ошибки, если:

| Что случилось | Что видит пользователь |
|---|---|
| История матчей закрыта настройкой Dota | подсказка включить «Expose Public Match Data» |
| Матчей меньше `MIN_GAMES` (50) | «слишком мало матчей», работает чистый L3 |
| OpenDota недоступна | «работаем без персонализации» |
| Steam ID не введён | «рекомендации по чистой модели драфта» |

Профиль привязан к запросу, а не к процессу: сервис один на всех
пользователей, и чужая статистика в чужой выдаче появиться не может.

## Доступ

Сайт закрыт HTTP Basic-аутентификацией. Причина не в том, что есть что
красть — записи и базы нет. Причина в вводе Steam ID: без калитки любой
прохожий может заставить сервер ходить в OpenDota произвольными
аккаунтами, а лимит там на IP, то есть общий на весь сервер.

```bash
python -m src.web.auth init друг1 друг2     # напечатает пароли
```

Пароли хранятся хешами (scrypt), файлы `configs/users.json` и
`configs/users.txt` — вне git. Обращения к OpenDota ограничены: 10 запросов
в минуту на пользователя, отдельным ведром на каждого.

Basic шлёт пароль в заголовке каждого запроса, поэтому **сайт нужно
поднимать под HTTPS** — см. `deploy/README.md`.
